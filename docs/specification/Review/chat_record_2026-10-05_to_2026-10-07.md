# Document review — chunked, bounded, and verified

A disciplined workflow for reviewing a long document with a person one idea at a time, where
**every change is visible and bounded and the tooling proves nothing else moved.** The point
is to keep the person's effort linear in the number of chunks — they should never have to
re-read the whole document to check that an edit did not silently break something elsewhere.

## When to use
The person wants to review / proofread / walk through a `.docx`, `.tex`, or PDF in small
pieces, commenting and editing as they go ("review this section by section", "one subsection
at a time", "let's go through the spec carefully").

## The five commitments (the reason this skill exists)
1. **Topic chunking.** Chunk by idea, not merely by heading number; group interrelated
   subsections so a single issue can be judged once.
2. **Interrelatedness manifest.** Maintain `Review/manifest.json` — the persistent touch-list
   mapping every figure/table/section to its source, its asserted facts/numbers, and its
   links. This is how interconnected information is managed (see "The manifest" below).
3. **No silent change.** Change ONLY what the chunk's decision requires. Anything else you
   notice, surface as a proposed follow-up for the person's call — never fold it in quietly.
4. **Change reported as a SUMMARY.** After editing, tell the person what changed in plain
   language (which passages, what the change does). Show verbatim before/after ONLY for light,
   surgical edits (a few words / one number) or when the person asks. Do not dump large diffs.
5. **Automated verification gate.** After every rebuild, run `verify_doc.py` and give the
   person a short PASS / FAIL report. They read the report instead of hunting for regressions.

## Model tiering

Work in this skill is not uniform in cost or in consequence: rendering a page is mechanical;
deciding whether a scope-diff flag is an authorized edit or a regression is not. Give each phase
the **cheapest tier that can be trusted with it**, and make any departure from that visible.

| Tier | Owns | Why |
|---|---|---|
| **Fable** | The chunking plan; the adversarial review of each chunk | The two places where a miss is unrecoverable. Bad chunking makes an issue invisible for the whole review; the adversarial pass is the only step that looks for what nobody asked about. |
| **Opus** | Invariant declaration, source-of-truth decisions, the SOURCE edit, gate-failure interpretation, the change SUMMARY | Load-bearing. Each can silently corrupt either the document or the person's picture of it — and the SUMMARY is the only thing they actually read. |
| **Sonnet** | Outline extraction, manifest skeleton, snapshots, `render_subsection.py`, rebuilds, running `verify_doc.py`, ledger updates | Deterministic or script-driven; the output is checkable by inspection, so a mistake surfaces immediately. |

These are tier names, not model identifiers — identifiers change. Resolve each to whatever
currently occupies that tier at run time.

### Rules

1. **The assigned tier is a floor, not an exact match.** Running a phase at a *higher* tier is
   always fine and needs no comment. Running it *lower* is the thing to control. So a session
   already at the top tier executes this skill unchanged — the convention only bites on the way
   down.
2. **Fable → Opus is pre-authorized.** Fall back without asking, but record it (rule 4). Note that
   a Fable session can be routed to Opus by Anthropic's safeguards without the running model being
   able to tell, so "am I actually Fable?" is not reliably self-answerable. Never gate execution on
   that answer — declare the tier you believe you are, and record it.
3. **Dropping to Sonnet for a Fable or Opus phase is a stop-and-ask.** Do not quietly run an
   adversarial review or a source edit at the mechanical tier. Name the phase, name the risk, let
   the person decide.
4. **Record the tier per chunk** in `Review/progress.json`, so a chunk handled at a fallback tier
   stays visibly re-reviewable instead of counting as signed off.

### Scheduling

Group work by tier; do not interleave. Assigning a tier step-by-step produces a dozen handoffs per
chunk — expensive with subagents, untenable without them. Run four passes instead:

- **Phase 0 — Intake, once per document.** Sonnet extracts the outline and seeds the manifest →
  Opus settles source-of-truth and declares the invariants → Fable sets the chunking and the
  review order, flagging which chunks are high-stakes.
- **Phase 1 — Present, per chunk (Sonnet).** Snapshot to `archive/`, render the one-page PDF,
  assemble the touch-list.
- **Phase 2 — Review, per chunk (Fable).** The adversarial pass. Propose decisions; change nothing.
- **Phase 3 — Execute, per chunk (Opus).** Edit the source, update the manifest, rebuild, run the
  gate, interpret the result, write the SUMMARY. The rebuild-and-gate sub-step is Sonnet work:
  delegate it if you can, otherwise just run it — a script's output does not depend on who typed
  the command.
- **Phase 4 — Ledger, per chunk (Sonnet).** Update `progress.json`, tier record included.

**With subagents** (Claude Code, Cowork): dispatch each phase to its tier and pass that phase's
inputs explicitly — a subagent inherits none of the conversation. Phase 2 needs the rendered page,
the touch-list, and the manifest slice; Phase 3 needs Phase 2's findings plus the person's
decision. This is where tiering actually saves anything.

**Without subagents** (claude.ai chat): one model runs every phase. Announce the phase and its
assigned tier at each boundary, apply rules 1–4, and ask the person to switch models only at the
Phase 1→2 and 2→3 boundaries — never mid-phase. If they decline to switch, that is a rule 3
answer: proceed and record it.

## Workflow

Tier in brackets is the floor for that step (see Model tiering above).

1. **[Sonnet] Map the document first.** Extract the ordered outline — every Heading 1/2/3, every figure
   caption, every table — and seed / update `Review/manifest.json`. Tell the person how many
   chunks, figures, and tables there are. Extraction is mechanical, but **deciding which numbers
   become invariants (and which get a `"phrase"`) is [Opus] work** — the whole gate rests on that
   choice, so do not leave it to the extraction pass.

2. **[Opus] Establish source-of-truth and version control BEFORE editing.** Determine how the
   document is produced. If it is generated from a script (docx-js / python-docx builder, or
   `.tex`), the SCRIPT + figure generators are the source and the `.docx`/PDF is a build
   artifact — edit the source, never the artifact. Confirm every figure has a LIVE source
   script recorded in the manifest; if a figure's source is missing, recover it (from the
   built docx `word/media/`, or an `archive/` snapshot) before touching that figure — a
   regenerated figure from a stale/guessed script silently drops content. Keep the sources
   under version control (git) if at all possible so every change is a diffable, revertable
   commit.

3. **[Sonnet] Present one chunk at a time** with `render_subsection.py` (bundled): a one-page PDF with
   running header, justified body, tables, and each embedded figure under its caption. Present
   it as a file card, list the chunk's touch-list from the manifest (what else shares these
   facts), and stop for comments.
   ```
   python render_subsection.py DOC.docx "7.2.2" out.pdf --header "Left | Right" --page "12"
   ```

4. **[Fable] Run an adversarial review of each chunk** as you present it: internal contradictions,
   conflicts with other sections (use the manifest links), code/safety gaps, numbers that do
   not reconcile, over-claims, missing caveats, redundancy, omissions. Rank serious items
   first; never soften a real safety or code issue. This runs every chunk — it is the point of
   a *careful* review.

5. **[Sonnet] Snapshot before every edit.** Copy the document (and the edited source script) into
   `archive/` with a dated name. Non-negotiable — the person may want to revert.

6. **[Opus] Edit the SOURCE**, obeying commitment 3 (no silent change). Update `Review/manifest.json`
   for every element you touched: its asserted numbers/facts and its links.

7. **[Sonnet to run, Opus to read] Regenerate + run the verification gate.** Rebuild the affected page(s), then run
   `python verify_doc.py DOC.docx --manifest Review/manifest.json --baseline archive/<prev>`
   and read the PASS/FAIL report. Do not present the chunk as done until the gate passes (or
   the person accepts a documented exception).

8. **[Opus] Report the change as a summary** (commitment 4) and re-present the regenerated page so the
   person sees the change land. Move to the next chunk on their cue.

## Gotcha: editing `.docx` tables with python-docx
Locate a table by its HEADER cells, not by a fixed `doc.tables[i]` index. Inserting or moving a
table (e.g. a new subsection's table) renumbers `doc.tables`, so a hard-coded index silently
targets the wrong table. Find the Document-History / target table by matching its first-row

## What the verification gate checks (`verify_doc.py`)
1. **Cross-references resolve** — every "§X.Y", "Figure N", "Table N" mentioned in the body
   points to an element that exists; no duplicates. Code/standard citations ("IBC §714",
   "NEC 220.60") and companion-document refs are recognised and NOT treated as internal.
2. **Inventory closed** — every referenced figure is embedded; every embedded figure has a live
   source script recorded in the manifest. Sources resolve against a LIST of candidate roots
   (see `--figures-root` below), so gating a build outside the canonical folder does not throw
   false "source missing".
3. **Term / number consistency** — for each manifest invariant, all elements that assert that
   key hold the same value (catches the "6 vs 7 modules" class automatically).
4. **Figure index complete** — if the document has a "Figure Index" appendix, it must list every
   real figure exactly once and nothing else. Catches the "new figure added, index not updated"
   defect (e.g. Figs 24/25, 18a/18b/21a/21b) and stale entries for removed figures.
5. **Prose / index number drift** — for any invariant that declares an optional `"phrase"` (the
   counted noun, e.g. `"HEPA module"`), the gate scans ALL text — prose AND table/index labels —
   for "`<number> … <phrase>`" and flags a number that disagrees with the invariant. This is what
   would have caught a figure-index label still reading "seven fanless HEPA modules" while the
   body and the invariant say six. Extends the number check out of the manifest into free text.
6. **Figure facts vs invariants** — the gate reads document *text*, not the pixels inside a
   figure, so a number baked into a figure image (e.g. "7 HEPA modules" drawn while the prose and
   every other figure say 6) is otherwise invisible. Each figure generator calls
   `figfacts.emit(name, hepa_modules=…, ffu_count=…)` to write a `<name>.facts.json` sidecar of
   what it ACTUALLY drew; a figure element that names it in `facts` is checked here against the
   invariants. This is the check that catches a stale/divergent figure image.
7. **Scope diff** — compared with a baseline snapshot, exactly the headings/figures/tables the
   person authorised changed; anything else is flagged, not shipped. `--intended` matches
   FUZZILY — a section number, an appendix letter, or a normalized substring — so
   `--intended "Figure Index"` matches the section key `"Appendix B.  Figure Index"`.

## Figure integrity — the three habits that stop figures drifting
The gate cannot read inside a rendered figure, so figures need discipline the text checks can't
supply. These three close the gap (learned the hard way — a figure showed 7 HEPA modules while the
source said 6, and a source diverged to an old single-hood concept):

1. **One source of truth for shared numbers.** Put cross-figure numbers in a single
   `figure_params.json` that the doc builder AND every generator import. A count then cannot
   diverge between a figure and the prose because there is only one copy.
2. **Regenerate on every build — never hand-stage.** Run `stage_all_figures.py` (regenerates each
   generator and copies its output into the staged set) before each doc rebuild, so a corrected
   source cannot leave a stale staged image behind. Any staged figure with no live generator is
   printed as UN-REGENERABLE so the gap stays visible.
3. **Emit facts and enrol every figure.** Each generator calls `figfacts.emit()` with the values
   it drew; every figure is a manifest element with `asserts` and a `facts` pointer. Check 6 then
   ties the figure's *actual rendered content* — not a hand-written claim — to the invariants.

Flags: `--manifest`, `--baseline`, `--intended <tokens…>`, and `--figures-root <dir>` (an extra
directory to resolve relative figure-source paths against — use it when the canonical file is
locked and you must gate a build staged elsewhere).

Here is the quantization-step procedure as the specification now stands, with the reasoning behind each part.

**What is being looked for.** An active stereo sensor computes depth from disparity. If disparity is quantized to a step q in pixels, depth is quantized to a step that grows with the square of distance: δZ_q = q·Z²/k with k = f_x·B. At the indicative geometry (f_x ≈ 688 px, B = 75 mm, so k ≈ 51,600 px·mm) and a Tier-A guess of q = 0.125 px, the expected quantum is 0.39 mm at 400 mm, 1.55 mm at 800 mm and 6.2 mm at 1600 mm. Two other things can hide or mimic it: the depth output's own least significant bit, which quantizes in millimeters rather than in disparity, and sub-pixel interpolation in the matcher, which can smooth the steps away in a patch average while single pixels still jump. The procedure is built to tell these three apart.

**Step 1, the passive look (Section 10, Step 8).** From the noise series A, at every station, the raw depth codes of the central 20 × 20 px patch are histogrammed over all 100 frames. The most common spacing between populated code levels is the measured quantum δZ_q(Z). If that spacing equals DEPTH_LSB_MM at every station, the output LSB is the quantizer and disparity quantization is invisible in this data, which is the cue to rely on the staircase instead. Otherwise q = δZ_q·k/Z² is computed per station, and it should come out constant if the quantizer works in disparity. This step costs no extra capture.

**Step 2, the active probe, the fine staircase (Section 6.2, Step 3).** At each of the three reduced stations, 400, 800 and 1600 mm, the robot carries the noise plate from Z₀ to Z₀ plus three expected quanta in steps of one tenth of a quantum, 31 steps, 10 frames at each, with the read-back pose logged at every step. The expected quantum uses the Tier-A q until A has measured one, which is why the planner prints the step sizes it chose: 0.039 mm at 400 mm, 0.155 mm at 800 mm, 0.62 mm at 1600 mm. Every visit is approached from below, so backlash does not enter. The read-back pose, not the commanded one, is the truth for the horizontal axis of the staircase plot; at 400 mm the commanded step is below the robot's repeatability, so this matters.

**Step 3, reading the staircase (Section 11.2, Step 5).** Sensed Z is plotted against read-back Z twice: for single pixels and for the 20 × 20 px patch mean. Plateau widths on the single-pixel curve give the measured quantum directly, which is compared with q·Z²/k from Section 10. A smooth patch-mean curve sitting over a stepped single-pixel curve is the signature of the sensor's interpolation dithering the quantizer: individual pixels still jump, but their phases differ, so the average moves continuously. A stepped patch mean means no dithering, and a staircase with no steps at all at the single-pixel level means the quantizer is finer than the noise can reveal, which is itself a result.

**Step 4, the consequence for the step ladder.** The ABAB step ladder measures the smallest detectable depth step δ_50. The quantum sets the scale of that result, which is why I flagged in C07 that the ladder is still fixed in millimeters while the quantum grows sixteen-fold across the range: at 1600 mm the whole ladder sits below one quantum. The proposal is to define the rungs as multiples of the expected quantum at each station, as the staircase already does.

**What is uncertain.** The Tier-A q of 0.125 px is an assumption; everything scales with it until A measures the real value. Whether the VSX3000 quantizes in disparity, in depth, or dithers is exactly what the three steps decide. And the staircase at 400 mm rests on the robot reporting its actual pose to 0.01 mm, which is now a stated equipment requirement but not a verified fact.

On your question, whether to measure sensor drift separately and omit the sentinels, my assessment, with the reasoning:

**What the sentinels measure.** A sentinel is the mounted target re-captured at the reference station, interleaved in time with the series. It sees the drift of the whole measurement chain along Z: the sensor's thermal depth drift, the robot's thermal growth, and any mechanical event, such as a mount slip or a bump, since the previous sentinel. The first sentinel after each mount is that mount's reference, so a jump between two sentinels on the same mount is a mechanical event, while a slow trend is thermal.

**What a separate drift measurement gives.** A dedicated run, with a static target on its own stand, the robot idle, continuous capture through warm-up and several hours, and the sensor temperature logged, gives drift as a function of time and temperature at far better time resolution than hourly sentinels. It is cheap, needs no robot time, and can run unattended. If the drift turns out to be a reproducible function of the sensor's own temperature reading after warm-up, that function plus the temperature log can correct the session without interleaved captures.

**Why omitting the sentinels is not advisable.**

- The separate run measures the sensor alone. The robot's thermal drift along Z is left out, and so is any mount or registration event during the session. The sentinels are the only in-session check that the drift function measured on another day, or on a static stand, applied on the day of the session.
- The saving is negligible. The sentinels cost 11 poses, 330 frames and about a minute of robot time per hour, under one percent of the session. The cost that mattered, re-mounting T2 for each sentinel, was removed at C06.
- Reproducibility of thermal drift across days is the uncertain part. Ambient airflow, the thermal state of the laser, and hysteresis between heating and cooling can make the temperature-to-drift map differ between the calibration run and the session. I cannot quantify this for the VSX3000 without data. Structured-light sensors typically drift at the tenth-of-a-millimeter level during the first 30 to 60 minutes and much less afterward, but that is a general expectation, not a measured property of this sensor.

**Recommendation.** Keep the sentinels, and add the separate drift run as an optional pre-session measurement, outside the budget, placed in Section 4 next to the warm-up step. The separate run supplies the drift-versus-temperature function and the warm-up time; the sentinels validate it on the day and catch mechanical events. If the separate run shows post-warm-up drift well below a tenth of σ_t, the sentinels become a check rather than a correction, and Step 11's correction would simply never trigger. Dropping them would then save a few minutes at the cost of having no in-session evidence.
